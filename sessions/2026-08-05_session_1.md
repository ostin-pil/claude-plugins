# Session 1: session-start acts on a stale read

**Date**: 2026-08-05
**Branch**: `feature/session-1-refetch` (branch-only, primary checkout)
**Type**: fix

## Context

The first session this repo has run under its own kit. It came out of an
aboard session that tripped the bug: `/session-start` briefed on a session
as in flight, offered to resume it, and by the time the answer came back
the branch, the worktree and the base commit were all gone. The fix is in
`session-start`; most of the session went into working out why a fix would
not have reached the machine that hit it.

## What happened

### 1. The distribution chain, and where it was broken

Fixing source does not reach a running Claude Code. The chain is source
repo, GitHub, marketplace clone, plugin cache, and two hops were stale:

| Stage | Was | Now |
| --- | --- | --- |
| `~/Projects/claude-plugins` | `6148459`, lifecycle-kit 0.2.0 | unchanged |
| `~/.claude/plugins/marketplaces/ostin-pil-plugins` | `5b31eb4`, 76 behind, last pulled 2026-06-17 | `6148459`, even |
| installed cache | pinned 0.1.0 from `4d5b33e` | 0.2.0 from `6148459` |

Two commands close it, and both are CLI surface rather than the `/plugin`
UI: `claude plugin marketplace update <name>` pulls the clone,
`claude plugin update <plugin>@<marketplace>` reinstalls. The second
requires a restart to apply.

The seven weeks of staleness turned out to cost nothing. Diffing the two
cached versions, exactly three files differ: `plugin.json`, the shellcheck
fix in `hooks/validate-manifest.sh`, and the `workflow_rule` default in
`lifecycle-manifest.template.md`. No skill file changed. So the running
skills were current, and the bug was genuinely in source rather than an
artifact of an old copy. Worth stating plainly, because the opposite was
assumed for most of the session.

### 2. The fix

`session-start` fetched in step 1 and acted on that snapshot in step 7,
with steps 2 through 6 (read logs, walk history, compose the briefing) in
between. That gap is minutes, which under a parallel session is enough for
the state to move.

Step 7 now re-fetches and re-reads the four facts branch birth rests on
(integration ref, worktree list, session branches, tree status), compares
against a snapshot step 1 is now told to keep, and corrects the briefing
before asking anything. The collision pre-flight reads the re-fetched refs
rather than step 1's, which is the half that matters for numbering: the
aboard incident also had another session claim the number this skill was
about to mint, and it had to renumber itself afterwards.

The version bump is part of the fix, not bookkeeping. `claude plugin
update` keys on the version in `plugin.json`, so without a bump the change
is unreachable by any installed copy.

### 3. What the update mechanism revealed

`claude plugin update prose-mint@ostin-pil-plugins` reports "already at the
latest version (0.1.0)" despite eight commits in source since its install,
two of them features. Version is the update key, and content that lands
without a bump never propagates. The same is true of knowledge-kit, with
two commits.

That gap is narrower than it first looked, for two reasons found while
checking it:

- The prose-mint plugin ships three markdown files. The tool itself comes
  from `uvx prose-mint`, so it is a PyPI release, not a plugin bump, that
  would reach consumers.
- `~/Projects/prose-mint` is a symlink to `~/Projects/claude-plugins/prose-mint`,
  and `bin/prose-mint` runs the package from the checkout. Every consumer
  resolving through that path (aboard's `bin/check-prose.sh` does) already
  runs live source, including all eight commits.

The symlink has a cost that belongs in the record: a consumer's prose gate
follows whatever branch this repo has checked out. While this session was
open, aboard's gate would have linted against `feature/session-1-refetch`.

### 4. No regression scenario, and why not

`benchmarks/lifecycle` is `setup.sh`, a fresh agent, `assert.sh` over
ground-truth git state. The failure needs the remote to change between the
agent's step-1 fetch and its step-7 re-read, and `setup.sh` runs before the
agent starts. Expressing it would take a sleep-based timer, which makes an
eval flaky. Left unwritten rather than written badly; it is a harness
design question, listed below.

## Decisions worth remembering

- **The version in `plugin.json` is the update key, not the content.** A
  change shipped without a bump is invisible to `claude plugin update`, no
  matter how many commits back it. This is why the fix carries a bump in
  the same commit.
- **The marketplace clone is a real git clone and pulls only when told.**
  Pushing to GitHub reaches nothing on its own. A plugin can be seven weeks
  stale with no signal anywhere in a session.
- **A symlinked checkout is a live dependency.** It bypasses both the
  release and the plugin, which is convenient until a consumer's gate
  starts following a feature branch.
- **A flaky eval is worse than a missing one.** The mid-run mutation this
  bug needs cannot be staged from `setup.sh`, and a timer would buy a test
  that fails for reasons unrelated to the skill.

## What's next

1. **A benchmark scenario for mid-run drift.** Needs a harness capable of
   mutating the remote between agent steps, deterministically. Worth
   designing, since every skill that reads then acts has this shape.
2. **Cut a prose-mint PyPI release** so the eight unreleased commits reach
   consumers who resolve through `uvx` rather than the symlink, and bump
   the plugin to 0.2.0 for the two features.
3. **Decide whether the symlink should stay.** It makes local iteration
   immediate and makes consumers track a working tree. Pick one on purpose.
4. **`sessions/INDEX.md`** is named by `log_index` in the manifest and does
   not exist. This is the first log, so the index has a single entry to
   hold whenever it is worth creating.
5. **knowledge-kit has two unreleased commits**, both marginal (a
   repo-wide docs commit, a CI commit). Fold into whatever bump comes next
   rather than cutting one for them.
