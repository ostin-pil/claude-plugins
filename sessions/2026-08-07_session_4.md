## Context

The one item with any depth to it was running the `stale-read` scenario against

## What happened

### 1. Session 3 credited a command that never ran

Section 4 of session 3's log said `uv cache clean prose-mint` "alone was not
enough". The command was reached for and never executed:

    Cache is currently in-use, waiting for other uv processes to finish
    (use `--force` to override)
    error: Timeout (300s) when waiting for lock on `/Users/costa/.cache/uv`

Concurrent `uvx` processes held the cache lock for the full five minutes. So
`--refresh` alone was the entire recovery, and the clean was no part of the
outcome either way. The log now says that. The correction is a single paragraph
in section 4; the rest of that log stands.

Two ways to read this. `uv cache clean` has a lock-contention failure mode worth
knowing about, particularly on a machine running parallel agent sessions that
each shell out to `uvx`. And a log written at the end of a session can record an
attempted command as a performed one, because "I ran X, then Y, and Y worked" is
how the session felt from the inside.

### 2. The stale-read scenario passes on both arms

Two runs, 2026-08-07, against installed `lifecycle-kit`:

| Arm | Version | Branch created | Verdict |
| --- | --- | --- | --- |
| pre-fix | 0.2.0, no re-read block in `session-start` step 7 | `feature/session-7-bench` | PASS, exit 0 |
| post-fix | 0.2.2, block present | `feature/session-7-bench` | PASS, exit 0 |

Neither was void; the shim landed `feature/session-6-concurrent` on the remote
in both. Both issued exactly three fetches, so even the fetch count does not
separate them.

The pre-fix arm's shim log shows how it got to 7. Its pre-flight ran
`git branch -a --list '*session-*'` and got nothing back, because the drift had
landed on the remote and no local tracking ref existed for it. It did not accept
that. It ran `git ls-remote origin`, which reads the remote directly and did show
the concurrent claim, chased the discrepancy through `show-ref`, `for-each-ref`
and the `remote.origin.fetch` refspec, re-fetched to materialize the tracking
ref, and only then computed `N`. Correct answer, arrived at by refusing to trust
a quiet fetch.

The post-fix arm's log is the skill executed literally: fetch, the four named
facts, then `N`.

### 3. Why retiming the drift will not rescue it

The temptation is to say the drift fires too early and to move it. It does not
help. The behavior under test is a process guarantee, that the fixed skill
*always* re-reads, and `assert.sh` observes only end state. A guaranteed re-read
and a lucky one leave byte-identical refs behind.

The fixed skill's re-read also runs before its pre-flight computes `N`, so any
drift early enough for a skill without the block to miss is also early enough
for a skill with it to catch, and any drift later than that is missed by both.
There is no window where the two arms diverge in git state. The remaining signal
is the agent's own account of why it re-read, and the harness rules that out by
design.

Kept, not deleted. The scenario still asserts something true and falsifiable,
that `session-start` does not mint a colliding number under a live concurrent
claim, and a future edit that regresses it fails here. What it cannot do is
attribute a pass to the fix. `scenario.md` now says both of those things, and
`benchmarks/lifecycle/README.md` gets a section on the limit, because it is a
property of the harness rather than of this one scenario.

### 4. The `2>/dev/null` on step 1's fetch, noted and not touched

Step 1 of `session-start` prescribes `git fetch <remote> --prune 2>/dev/null`.
Git writes fetch progress, including the `* [new branch]` lines, to stderr. The
redirect exists so that being offline is not an error, and it also throws away
the one signal that says the fetch did real work. In the pre-fix arm this is
what made a fetch that pulled a new remote branch look identical to a no-op.

This is a genuine observation about the skill text and it is not fixed here.
Changing a skill mid-session and then reasoning about a benchmark run against
its installed predecessor is how the record gets confused. Carried to next.

### 5. The pre-merge tags: documented, not deleted

`v1` and `v0.1.0` sit before the subtree merge that absorbed prose-mint, when
the package was at the repo root. `main` has it under `prose-mint/`, so
`git diff v0.1.0..main` reports the whole package deleted and re-added, about
450 stat lines of nothing.

    git diff --stat v0.1.0..main             # ~450 lines of path moves
    git diff --stat v0.1.0 main:prose-mint   # 24 files
    git diff --stat v1     main:prose-mint   # 42 files

What the investigation turned up, before deciding:

- Both tags are annotated and both are reachable from `main`. The subtree merge
  preserved the history, so no objects depend on the tag names surviving.
- Neither is on this repo's remote. `git ls-remote --tags origin` lists only
  `prose-mint-v0.1.1`. They exist in clones that also fetched the ProseMint
  remote, which means a local `git tag -d` is not a remote-affecting action at
  all, contrary to the assumption going in.
- `prose-mint/CHANGELOG.md` records `v1` as deliberately frozen at `aa57678` for
  consumers on `uses: ostin-pil/ProseMint@v1`. That ref resolves in the
  `ostin-pil/ProseMint` repo, not this one, so this repo's copy of the tag is
  not what keeps those consumers working.
- `prose-mint-v0.1.1` is post-merge and diffs cleanly, so the trap is specific
  to these two.

Documenting won on the grounds that deleting fixes the wrong thing. The
confusion is caused by the path move, not by the tags existing, and it recurs
for anyone who fetches the ProseMint remote again or reaches for a diff after
reading the CHANGELOG's `@v1` note. A README section helps every reader of the
repo; a local tag delete helps one checkout. The deletion is still available and
costs nothing, so it is offered to the operator rather than taken.

## Decisions worth remembering

- **A test that passes on both sides of the fix has told you nothing about the
  fix.** Session 2 predicted this exact outcome and named it in advance, which
  is the only reason the result was legible instead of reassuring.
- **Outcome assertions cannot see a process guarantee.** Ground-truth git state
  is the right thing to assert, and where a skill's contribution is "always does
  X" rather than a distinct end state, a competent agent reaching the same end
  state by another route is indistinguishable from compliance.
- **Silencing stderr silences the evidence too.** `2>/dev/null` on a fetch buys
  offline tolerance and sells the `* [new branch]` line that says the world
  changed.
- **Delete what is confusing, or document what is confusing, depending on where
  the confusion lives.** The tags were not the problem; the path move was, and
  it survives any tag delete.
- **A deferral without a trigger is not a decision.** knowledge-kit's bump was
  deferred three times on the same reasoning before anyone wrote down what would
  end the deferral.
- **Check whether the thing is remote-affecting before treating it as one.**
  `git ls-remote --tags` settled in one command an assumption that had shaped
  the whole approach to the tags.

## What's next

1. **Open design question for the operator: can this harness test a process
   guarantee at all?** `stale-read` is the first scenario where the skill's
   contribution is "always re-reads" rather than a distinct end state, and
   `assert.sh` cannot see the difference. Three directions, none obviously
   right. Accept the limit and treat such scenarios as regression guards only.
   Assert on observable process rather than self-report, for instance by having
   the git shim log every call and asserting on the *shape* of the call
   sequence, which is ground truth rather than testimony, though it couples the
   assertion to one correct implementation. Or design drift that a
   non-re-reading skill structurally cannot survive, if such a window exists.
   Not resolved here; it needs a call on what the benchmark is for.
2. **`session-start` step 1's `2>/dev/null`.** Section 4 above. A fetch that
   pulls a new remote branch should not look like a no-op. Any fix has to keep
   offline from being an error, so probably capturing stderr and reporting it
   rather than dropping it.
3. **The symlink pinning decision**, carried from sessions 1 and 3 and still
   open. Published 0.1.1 is byte-identical to source, so pointing aboard's
   `bin/check-prose.sh` at `uvx prose-mint` costs nothing today.
4. **Optional, operator's call: delete the local `v0.1.0` and `v1` tags.**
   Recommended against above, but it is a one-liner and it makes this checkout
   match a fresh clone. `git tag -d v0.1.0 v1`. Recreate with
   `git tag -a v1 aa57678` and `git tag -a v0.1.0 7f1edc8` if regretted. Both
   commits stay reachable from `main` either way.
5. **knowledge-kit bump when `skills/`, `bin/`, `templates/` or
   `manifest-keys.md` drifts.** Not before.
