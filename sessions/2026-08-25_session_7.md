# Session 7: the linter could not print its own findings

**Date**: 2026-08-25
**Branch**: `feature/session-7-utf8` (worktree `.claude/worktrees/session-7-utf8`)
**Type**: fix

## Context

Session 6 ran the suite on Windows and found five failures that reproduced on a
clean `main`. They were reported as one bug, a `UnicodeEncodeError` from the
robot emoji in an `ai-attribution` fixture. They were three.

## One: the tool crashed on its own output

A finding quotes the offending line, so the output carries whatever the scanned
document carries. On Windows a redirected stdout falls back to the ANSI code
page, and cp1252 cannot encode an ASCII arrow, the robot emoji in an
AI-attribution footer, or any Cyrillic at all. Two of the eight structural
categories and every Russian document killed the process, on exactly the input
the scanner exists to report. Russian documents are a documented feature with
their own README section and a `cyrillic_em_dash_exempt` rule.

It failed only when redirected, because a real Windows console takes a different
path in CPython. An interactive run looked healthy while CI and any
`prose-mint ... | tee` died, which is the wrong way round for a tool whose main
venue is a pipeline.

`main()` now reconfigures stdout and stderr to UTF-8. It overrides
PYTHONIOENCODING on purpose: the alternative to writing UTF-8 is not writing the
finding. A stream with no `reconfigure` is left alone, which is what
`redirect_stdout` hands the in-process tests.

**The correction that matters.** Session 6 recorded that the em dash was among
the characters cp1252 could not encode, and used that to argue the tool crashed
on its commonest finding. That was wrong. cp1252 encodes the em dash at 0x97,
and it is precisely because the most-reported category always worked that this
survived so long. There is a test pinning the fact, because the diagnosis
depends on it.

## Two: the walk order depended on the platform

`sorted()` over `Path` objects compares a case-folded key on Windows and raw
bytes on POSIX. So `README.md` sorted before `meeting.md` on Linux and after it
on Windows. The walk order is the report's order, so one corpus produced two
different documents depending on the machine, and the byte-for-byte golden was
unmatchable on one platform by construction.

This is the one with reach beyond Windows. Any cross-machine diff of `bulk`
output carried reordering noise, and the repo's central claim is that this
output is stable enough to compare byte-for-byte.

Sorting on the POSIX string is a no-op on Linux and fixes the order on Windows.

## Three: the suite made the same assumption the CLI did

Sixteen `subprocess.run(..., text=True)` calls decoded child stdout with the
locale encoding, so a fixed child would still have mismatched. Five
`read_text()` calls read UTF-8 fixtures back as cp1252, which is why
`test_explicit_config_wins_over_discovery` saw no em dash in a document that
plainly contained one: the file was written UTF-8 and read back as three cp1252
characters.

Golden comparison also normalises path separators now. The goldens were captured
on POSIX and `bulk` prints native separators, which is right for a reader on
Windows and wrong for a byte compare. The goldens hold no literal backslash, so
the swap is lossless and the output stays native.

## What the new tests do differently

Every encoding test forces `PYTHONIOENCODING=cp1252` on the child, which
reproduces the Windows failure on any platform. Without that they would pass
everywhere UTF-8 is the default and guard nothing, which is exactly how the
original bug reached a repo with a 150-test suite and a frozen corpus.

## Build status

`uv run --with pytest --with ./prose-mint python -m pytest prose-mint/tests`
gives 151 passed, 1 skipped, 0 failed on Windows. The baseline on `main` was 139
passed, 5 failed. Six tests added.

Linux behaviour is unchanged by construction: every fix is a no-op where UTF-8
output and byte-order sorting are already the default, which is why CI had been
green throughout.

## Still open

- The upstream Untype scanner almost certainly carries the same two production
  defects, since both were ported verbatim. `test_source_drift.py` guards
  category parity and would not see this. Worth a look on a machine that has the
  checkout.
- `bin/prose-mint` and the MCP server were left alone. FastMCP owns its own
  stdio framing and reconfiguring it from here could break JSON-RPC.
