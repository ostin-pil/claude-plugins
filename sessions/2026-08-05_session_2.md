## Context

## What happened

### 1. The release is blocked on PyPI, not on us

Session 1 listed "cut a prose-mint PyPI release" as though nothing had been
attempted. Something had. `prose-mint-v0.1.1` was tagged and pushed on
2026-07-27, the release workflow ran, the build job passed, and the publish job
failed in 14 seconds:

    invalid-publisher: valid token, but no corresponding publisher

PyPI has no Trusted Publisher registered for the project. `release.yml`'s own
header documents this as one-time manual setup on pypi.org, and it was never
done, so the pipeline has never once published. PyPI still serves 0.1.0.

Two things follow. The pipeline itself is fine and needs no change. And a
retry of 0.1.1 would be wrong anyway: that tag points at `07bd6de`, and
`c9cced9` (the PR-body ruleset feature) landed after it, so the next release is
0.2.0 with a changelog entry recording that 0.1.1 was cut and never shipped.

Handed back rather than worked around. The claims the failed run prints are
exactly what pypi.org wants: owner `ostin-pil`, repository `claude-plugins`,
workflow `release.yml`, environment `pypi`.

### 2. The harness could always do this

`benchmarks/lifecycle` already ships `gh-mock/gh`: a stand-in placed first on
PATH, configured by env, logging every call. Session 1 concluded a mid-run
mutation would need a timer without looking at that. The same shape applied to
`git` solves it exactly, and deterministically.

`git-mock/git` forwards every invocation to the real git and, after the first
`fetch` returns, pushes a branch to the bare remote. Counting fetches is what
makes it exact; a sleep would race the agent's reading speed. It takes
`GIT_MOCK_REAL` as an absolute path because the shim is first on PATH and
cannot resolve `git` by name, and every inner call in the drift step uses that
path so the shim does not recurse into itself.

### 3. The scenario discriminates on the number, not the base

The first design tested the branch's base commit, which does not work: step 7's
own option text runs `git fetch` before `git switch -c`, so even a skill that
never re-reads ends up branching off a current ref. The number is different.
`N` is computed before the question is asked, from whatever the pre-flight saw,
so it is the value that carries the stale snapshot into the outcome. That is
also what actually went wrong in aboard, where two sessions picked 41.

So: logs through session 5, no session branches, every pre-flight source tops
out at 5. The shim lands `feature/session-6-concurrent` after the first fetch.
A skill acting on its step-1 snapshot mints 6 and collides. One that re-reads
mints 7.

### 4. Void is not pass

`assert.sh` exits 2 when the concurrent branch never reached the remote. This
matters more here than in the other scenarios: if the drift fails to fire, the
agent never faced the collision, and 6 is then the answer a correct skill and a
broken harness both produce. A void run reported as a pass would be worse than
no test.

### 5. Verified, but not end to end

The mechanics were exercised against hand-staged git state: void exits 2, a
`session-6` branch exits 1, a `session-7` branch exits 0, the shim fires once
on the first fetch, handles `git -C <path> fetch` from an unrelated cwd, and
does not trigger on non-fetch calls. The agent leg has not been run, so
`scenario.md` records the baseline as pending instead of claiming a pass. The
other five scenarios all carry a real baseline; this one should not pretend to.

## Decisions worth remembering

- **Look at the harness before declaring a test impossible.** The gh mock had
  been the answer for two sessions. "Needs a harness that can do X" was a
  conclusion reached without reading the harness.
- **Test the value that carries the staleness.** The branch base looked like
  the obvious assertion and is not discriminating, because the branch-birth
  command fetches on its own. The session number is computed before the
  question and never revisited, so it is where a stale read survives.
- **A benchmark that cannot fail correctly is a liability.** With drift as the
  precondition, a no-drift run and a correct run are indistinguishable by
  outcome. The void exit is what keeps the scenario honest.
- **Count events, do not sleep.** The shim fires on the first fetch, whenever
  that is, so the scenario does not depend on how fast the agent reads.
