# Session 3: prose-mint 0.1.1 actually published

**Date**: 2026-08-05
**Branch**: `feature/session-3-prose-mint-release` (branch-only, primary checkout)
**Type**: chore

## Context

Session 2 recorded the prose-mint release as blocked on a missing PyPI Trusted
Publisher, inferred from a workflow run that failed on 2026-07-27 with
`invalid-publisher`. The operator reported the publisher was in fact registered.
Re-running that same run published on the first attempt, so the inference was
wrong and the release had been one button away for eight days.

The session then found that the version to publish was not the one planned.

## What happened

### 1. The inference was wrong, and the shape of the error is worth keeping

Session 2 read "failed with `invalid-publisher` on 2026-07-27" as "was never
configured". Those are different claims, and only the first was evidence. PyPI's
publisher configuration is not readable from here at all; it needs the project
owner's account. `gh run rerun 30300110569 --failed` completed green, which
means the publisher was registered at some point after that run and the failure
log had simply stopped being current.

Nothing in the repo needed changing for this. The pipeline was correct the whole
time.

### 2. 0.2.0 was the wrong version

Session 2's plan was 0.2.0, on the grounds that a feature landed after the
`prose-mint-v0.1.1` tag. It did, but not in the package:

    git diff --stat prose-mint-v0.1.1..main -- prose-mint/prose_mint/ \
        prose-mint/pyproject.toml prose-mint/tests/     # empty

The Python package is byte-identical to that tag. Everything after it touched
`README.md` and `action.yml`, so `c9cced9`'s `pr-body-config` is a GitHub Action
input, not package code. 0.1.1 was already the right version, already cut,
already tagged at the right content. Bumping would have published a version
whose only distinction from 0.1.1 was the number.

### 3. What the release actually delivers, checked rather than assumed

The published 0.1.0 sdist was downloaded and diffed against the source package.
Two files differ, `__init__.py` and `cli.py`, and the substantive change is
`--no-config`, absent from 0.1.0 and present in source. So the release is small
but real, and the CHANGELOG's existing 0.1.1 entry describes it accurately.

    PyPI before: 0.1.0
    PyPI after:  0.1.0, 0.1.1  (wheel + sdist, requires-python >=3.11)

### 4. uv's index cache says a fresh release does not exist

For several minutes after publishing, `uvx --from 'prose-mint==0.1.1'` answered:

    Because there is no version of prose-mint==0.1.1 ... unsatisfiable

while `pypi.org/simple/prose-mint/` listed the file and the JSON API showed both
artifacts unyanked. It was a stale local index, not propagation. `--refresh`
resolved 0.1.1 immediately, and the unpinned `uvx prose-mint` then reported
0.1.1 too. `--refresh` on its own was the whole recovery.

`uv cache clean prose-mint` was reached for first and never ran at all:

    Cache is currently in-use, waiting for other uv processes to finish
    (use `--force` to override)
    error: Timeout (300s) when waiting for lock on `/Users/costa/.cache/uv`

Concurrent `uvx` processes held the cache lock for the full five minutes, so the
clean never touched the cache and was no part of the fix.

Worth knowing before concluding a release is broken: uv will state flatly that a
version does not exist when it means its cached index does not list it.

### 5. The plugin had real drift, unlike the package

`prose-mint/plugin/` changed since its 2026-06-16 install: the command and the
skill dropped `~/Projects/prose-mint/bin/prose-mint` as fallback in favour of
`uvx prose-mint`, which needs no checkout at a fixed path. That never reached an
installed copy, because `claude plugin update` keys on the version and the
plugin sat at 0.1.0. Bumped to 0.1.1 to match the package.

This is the same trap session 1 hit with lifecycle-kit, from the other side: the
package was fine and the plugin was stale, where before the skills were fine and
the assumption was that they were stale.

## Decisions worth remembering

- **A failed run is evidence about a moment, not about now.** Especially for
  state held in a third-party console that cannot be read from here. Re-running
  is cheaper than reasoning about whether the cause still holds.
- **Check what a version bump would actually ship before choosing the number.**
  The commits after the tag were real and none of them were in the package. A
  diff of the shipped paths settles it in one command.
- **`uv` reports a stale index as a missing version.** The wording is
  indistinguishable from a genuinely absent release. Confirm against the simple
  index before believing it, and reach for `--refresh`.
- **Version is the update key, on both sides.** lifecycle-kit taught this with a
  stale plugin over current skills; prose-mint repeats it with a stale plugin
  over a current package.
